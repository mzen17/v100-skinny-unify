# Prefill investigation, 2026-09-04 (2-GPU box)

Box: Tesla V100-PCIE-16GB (PCIe gen3 **x8**) + Tesla PG500-216 32 GB (x16),
KVM guest, no GPU P2P, 8 vCPU. Serving config unless noted: `KVDT=fp8`,
`MML=65536`, `GMU=0.92`, `MBT=4096`, `MNS=1`, text-only, k=3 chain-MTP.
Harness: `scratchpad/prefill_bench.py` (streaming `/v1/completions`, TTFT =
time to first streamed token, prefill tok/s = prompt_tokens / TTFT, n=1).

## Where a 3.6k-token TP=2 prefill spends its GPU time (torch profiler, rank 0)

| item | ms | share of busy |
|---|---:|---:|
| `ncclDevKernel_AllReduce_Sum_f16_RING_LL` (262 calls, 5.4 ms each) | 1420 | 43% |
| cuBLAS `s884gemm 128x128` (522 calls, ~88 TFLOPS) | 1006 | 30% |
| FP8 prefill reconstruct: `index_put` unpack + cast + scale | ~550 | 17% |
| NVFP4 `qpn_dequant` (recon route) | 164 | 5% |
| attention (paged d256 + dense) | 95 | 3% |
| GDN (tilelang chunk kernel) | 71 | 2% |

The GEMMs already run near the V100 practical ceiling. The all-reduce is
link-bound: standalone 2-GPU NCCL on a [4096,5120] fp16 buffer measures
11.9 ms default, 8.6 ms with `NCCL_ALGO=Tree`, 20 ms LL128 -- nothing gets
close to a NVLink or x16 figure, because the traffic bounces through host
memory over the x8 slot. Prompts are split at mamba block boundaries (1648
tokens), so a 3.6k prompt runs as 3296 + 316 tokens = 2 x 128 all-reduces.

## Change 1: fused QPN8 unprepack+dequant kernel (`ext.qpn8_dequant`)

Replaces the three-pass torch reconstruct (advanced-index gather with a
~300 MB int64 index transient, fp8->fp16 cast, scale multiply) with one
memory-bound kernel. Bit-identical to the torch path (the kernel rounds the
tile scale through fp16 exactly as the torch path did), validated on the
three per-rank FP8 shapes; timings per call:

| N x K | torch reconstruct | fused | speedup |
|---|---:|---:|---:|
| 8192 x 5120 | 2.98 ms | 0.54 ms | 5.5x |
| 5120 x 3072 | 1.40 ms | 0.21 ms | 6.8x |
| 7168 x 5120 | 2.61 ms | 0.47 ms | 5.5x |

The stock 1.5.0 column is the upstream wheel unmodified (env `skinny15`),
same CLI shape, `--max-model-len 32768` because its TurboMind weight path
leaves only 1.39 GiB for KV at GMU 0.92 (64k needs 1.45). It resolves
`--kv-cache-dtype fp8` to **e5m2** on SM70 and announces its "exact Split-D

is a TP4 NVLink figure; on this PCIe box it hits the same all-reduce wall.

PP2 = `--tensor-parallel-size 1 --pipeline-parallel-size 2`, 32 GB card as
stage 0, `VLLM_SKINNY_RECON_MAX_BYTES=536870912` (at TP=1 the full-width
gate/up transient is 356 MB; with the default 256 MiB cap the trunk silently
fell to the 2x-slower `wmma_recon` route and PP measured only 672-956 tok/s),
`custom_ops=['none']`. PP removes every all-reduce; the V1 scheduler keeps
two prefill chunks of one request in flight, so single-chunk prompts match
TP2 and longer prompts gain 25-40%. Greedy outputs from the PP server were
identical between the wmma and recon routes. Decode without speculation
under PP is ~35 tok/s (stages run back to back).

## Rejected / measured-negative

- NCCL protocol/algorithm/buffer tuning: see figures above; link-bound.
- Async scheduling with PP: doubles in-flight activations, OOMs the 16 GB
  stage at an 8k prompt.
- Padding the dequant kernels' shared-memory rows to kill bank conflicts:
  bit-identical, no measurable speedup; reverted.
- torch profiler under PP: CUPTI "External init callback must run in same
  thread as registerClient" kills the stage-1 worker.

## PP=2 with MTP (k=3): boots, but not a serving configuration

Getting the drafter to run under PP needed: `SupportsPP` on `Qwen3_5MTP`, an
always-embed predictor forward, a drafter-owned embedding when PP>1
(`fork_patches/qwen3_5_mtp.py`), last-rank guards around the runner's
drafter references and a draft-token broadcast for the PP+async path
(`fork_patches/gpu_model_runner.py`). Because the drafter's 2.5 GB
embedding copy and the target's copy both have to fit, the 16 GB card takes
stage 0 with `VLLM_PP_LAYER_PARTITION=26,38`, `GMU=0.93`,
`--kv-cache-memory-bytes 2362232012` (64k needs 1.88 GiB/rank),
`--no-async-scheduling` (upstream's PP+async token broadcast asserts one
sampled token per request, which speculation violates) and
`inductor_compile_config: {combo_kernels: false, benchmark_combo_kernel:
false}` (autotune otherwise allocates a 2.37 GiB copy of the embedding table).
All eleven boot gates pass. Measured:

| prompt tokens | prefill tok/s | decode tok/s (k=3) |
|---:|---:|---:|
| 464 | 662 | 17.5 |
| 3617 | 1052 | 17.0 |
| 7230 | 1063 | 15.9 |
| 14497 | 1010 | 24.0 |
| 28987 | 881 | 12.6 |

The uneven split costs the prefill gain, and decode is 3-6x slower than TP2
because the two stages and the drafter run strictly back to back with a
synchronous scheduler. PP is therefore a **spec-off, prefill-only** mode.

## Change 2: host-memory 2-rank all-reduce (`kernels/skinny_ar.cu`)

The fork's custom all-reduce needs GPU P2P, which this KVM guest lacks, so
every decode all-reduce went through NCCL's LL protocol at 44 us for 40 KB.
`skinny_ar` does the exchange inside one kernel: each block writes its chunk
to a pinned host slot shared by both ranks, fences, raises a per-block flag,
spins on the peer's flag, reads the peer's chunk straight from host memory
and adds. Double-buffered by call parity, call counter in device memory
(CUDA-graph safe), exact fp16 sum (bit-identical to NCCL, verified over 900
random calls incl. graph replay).

| M rows x 5120 fp16 | NCCL in-server | skinny_ar standalone |
|---:|---:|---:|
| 4 (40 KB) | 44 us | 27 us |
| 8 (80 KB) | - | 44 us |
| 16 (160 KB) | - | 70 us |

Phase split on GPU0 (PCIe gen3 x8): kernel write of 40 KB to host 13 us,
read 12 us; incremental cost 0.15 us/KB in either direction, i.e. the link,
plus ~6 us fixed per phase. DMA-engine copies are worse here (20-33 us per
op). A chunk-pipelined variant that overlaps the read of chunk j with the
write of chunk j+1 measured slower (per-chunk fence/poll latency) and was
dropped; more blocks slow the writes, 10 blocks is the sweet spot.

Routing lives in `fork_patches/cuda_communicator.py`: fp16, contiguous,
16 B aligned, <= 256 KB (`VLLM_SKINNY_AR_MAX_BYTES`), TP group of exactly
2; everything else (all prefill traffic) stays on NCCL. `VLLM_SKINNY_AR=0`
disables it.

| decode tok/s (mean of the 3 prompts) | run 1 | run 2 | run 3 | mean |
|---|---:|---:|---:|---:|
| before | 102.8 | 108.8 | 80.8 | 97.5 |
| skinny_ar | 112.8 | 119.8 | 88.6 | **107.0** |
| skinny_ar, re-boot | 112.3 | 119.9 | 88.2 | 106.8 |

Greedy outputs identical to the pre-change server on the probe set; prefill
unchanged (1204 tok/s at 3.6k). In-server the kernel averages 61 us on rank
0 and 89 us on rank 1 because it also absorbs inter-rank launch skew, as
NCCL did; the saving is the 17 us of transfer per call.

## Measured and not adopted

- **k=7 at short context on these prompts: 90.8 tok/s vs 106.8 at k=3**
  (113.4 / 85.0 / 74.1). Acceptance on the synthetic prompts decays past
  three drafts; the README's k=7 recommendation stands for its own cells.
- NCCL small-message knobs (PROTO, ALGO, NTHREADS, MAX_NCHANNELS, BUFFSIZE,
  SHM_USE_CUDA_MEMCPY): 110-130 us standalone for all, no lever.
- Async scheduling: already on by default in this build (auto).
- Dynamic draft vocab: the GPU LRU path requires an fp16 lm_head; ours is
  QPN2 from checkpoint codes, so it cannot be enabled without a reduced
  QPN2 head (est. ~2%/round).

## Remaining headroom (fork's own per-phase MTP profile, steady interval)

target forward 23.9 ms GPU, target logits 0.8, rejection 0.08, three draft
forwards 0.85 ms each plus 0.5 ms sample each, state-update CPU 1.2-3.4 ms,
per-step draft attention-metadata rebuild ~0.8 ms CPU (mostly hidden behind
the target forward by async launch). Round wall ~32 ms vs ~29 ms GPU: about
3 ms of host gaps. Candidates: fuse the GDN per-layer decode tail (~2.6 ms
GPU), capture the drafter steps with their attention in a FULL graph to
remove the per-step metadata rebuild, and the state-update CPU path.

## Theoretical decode ceiling on 2x V100 and the accounting of the gap

Bytes each rank must read per k=3 round (TP=2 shards, checkpoint formats):

| weights | bytes/rank |
|---|---:|
| NVFP4 MLP trunk, 64 layers x (50.1 + 25.1) MB | 4.81 GB |
| FP8 projections, 48 GDN x 57.7 MB + 16 attn x 52.4 MB | 3.61 GB |
| verify lm_head (NVFP4) | 0.18 GB |
| drafter, 3 steps x (fp16 MTP layer ~0.38 GB + lm_head 0.18 GB) | 1.68 GB |
| total per round | **~10.3 GB** |

At the measured 879 GB/s read ceiling that is 11.7 ms per round. With the
observed 3.46 accepted tokens per round the ceiling is **~295 tok/s**; at
the k=3 maximum of 4 tokens per round, ~340. Without speculation a single
stream is capped at 8.6 GB / 879 GB/s = 9.8 ms, i.e. **~100 tok/s**, which is
why chain-MTP exists at all on this hardware. Measured: 32.3 ms per round,
107 tok/s, 37% of the ceiling. The 20 ms gap, from the rank-0 profile:

| gap component | ms/round | why |
|---|---:|---|
| weight kernels at 71% of roofline instead of 100% | +5.0 | GEMV shapes are occupancy/latency bound (small-N projections launch 64-112 blocks on 80 SMs); qpn2 tuning is exhausted, a 128-bit prepack is the only lever left |
| ~1,600 non-GEMM kernels: norms, residual adds, RoPE, KV write, GDN conv/gating/recurrence/norm, SiLU-mul, casts, scatter/gather | +9.0 | 64 layers x ~25 kernels; each 3-6 us regardless of the 4 rows it touches; fusion is the only fix |
| 138 all-reduces + skew | +4.5 | TP=2 needs two sync points per layer; 27 us each after skinny_ar |
| host gaps | +3.0 | input-batch update, drafter metadata rebuild, launches |

A realistic best case on this hardware (85% roofline, tail halved by fusion,
x16 link, host gaps trimmed) is ~20 ms per round: ~170 tok/s at today's
acceptance, ~200+ on text where k=7 holds. Beyond that only more tokens per
weight read moves the number: acceptance length or concurrent sequences.

# Decode tail work, 2026-09-04 (later)

Everything below is measured on rank 0 per decode round from torch-profiler
kernel sums (precise), because wall-clock tok/s on this VM drifts by +-5%
between and even within boots (clocks, temperature and power are flat and
no throttle reason is set; the drift is host-side).

| per round, rank 0 (k=3, short context) | before tail work | after |
|---|---:|---:|
| kernels launched | 1,880 | 1,555 |
| all-reduce kernels incl. wait for the peer | 8.5 ms (avg 61 us) | 3.6 ms (avg 26 us) |
| copy / fill glue | 1.45 ms | 0.67 ms |
| inductor triton norms | 1.18 ms | 0.87 ms |
| cutlass wmma + split-K for the `ba` projection | 0.66 ms | 0 (GEMV 0.39 + split 0.11) |
| **GPU kernel time per round** | **33.8 ms** | **27.4 ms** |

Changes, all bit-identical or within one fp16 ulp, greedy outputs identical
on the probe set:

- **Fused all-reduce + residual + Gemma RMSNorm** (`skinny_ar.cu`
  `all_reduce_gemma_norm`, one block per row, fp32 residual out) behind the
  fork's own `sm70_tp2_all_reduce_gemma_rms_norm` op. The fork's inductor
  fusion pass (`allreduce_rms_fusion.py`) required the P2P custom
  all-reduce and, on this model, matched nothing because
  `GemmaRMSNorm._forward_static_with_residual` re-casts the fp32 sum
  (`x = x.float()`) and that same-dtype `prims.convert_element_type` is
  still in the graph when the pass runs; torch's `fwd_only` tracer strips it
  from the pattern. Fix: accept `skinny_ar` in the gate and register a second
  pattern that calls the prim explicitly, traced with
  `run_functional_passes=False`. Now ~77 of ~138 all-reduces per round come
  out fused (the MLP-down boundaries; the GDN out_proj all-reduce lives
  inside the opaque GDN custom op and the full-attention output is copied
  into a preallocated buffer, so those two boundaries stay unfused).
  Side effect: with fewer launches the two ranks stay in lockstep, and the
  all-reduce kernel time fell from 61 to 26 us average, i.e. the skew is gone.
- **`gdn_split3`**: one launch for the q/k/v split (`rearrange_mixed_qkv`)
  instead of three strided reshape copies plus a cat; exact.
- **`gemv_f16`**: the fp16 `in_proj_ba` projection in one kernel (templated
  row count, 16 B loads) instead of cutlass wmma + split-K; the live call is
  in `qwen3_5.py`'s subclass `forward_cuda`, not the GDN base file. Within
  one fp16 ulp of cuBLAS, closer to fp32 truth.
- **CPU pinning** of the two workers, engine core and API server to disjoint
  core pairs in the launcher: +1.1% in an interleaved A/B.

Wall-clock stayed in the 99-108 tok/s band on the 3-prompt bench, i.e. the
6.4 ms/round of GPU time removed did not shorten the round. **The host path
is now the limiter**: with ~27 ms of GPU work per round the two worker
processes (each ~100% of a vCPU) and the engine core cannot feed the GPUs
faster than ~30 ms per round. The remaining host cost, from the eager
stack-attributed profile: the inter-round input-batch update (`_e5_apply_ints`,
`_update_states_after_model_execute`), the drafter's per-step attention
metadata rebuild (`build_per_group_and_layer_attn_metadata`,
`_update_smallq_decode_metadata`, `_split_paged_kv_cache`, ~143 eager
kernel launches and 67 small H2D copies per round), and the all-gather /
argmax path. Capturing the drafter steps with their attention in a full CUDA
graph is the change that would move this; it is engine work in the fork's
proposer and attention backend, not started.

Not adopted: an `arange`+scatter/gather pair per GDN layer (~1 ms/round)
that appears only in graph mode could not be attributed (the fork replays
its own captured graphs even with `cudagraph_mode: NONE`; `--enforce-eager`
changes the kernel set).

## Numerics gate for the tail changes, and shipped defaults

Decode-shaped probe (`scratchpad/kl_probe.py`: greedy, top-5 logprobs per
generated token, three flat synthetic prompts x 200 tokens plus four natural
prompts x 64, compared only at positions with identical context):

| comparison | first divergence (synthetic / natural) | top-1 agreement | top-5 KL mean / p99 |
|---|---|---:|---:|
| fused AR+norm vs off (both with GEMV) | 48, 81, 54 / none | 439/439 | 1.7e-3 / 4.7e-2 |
| GEMV vs cuBLAS `ba` (fusion off both) | 48, 105, 58 / none | 467/467 | 4.1e-3 / 1.0e-1 |
| shipped defaults vs GEMV-off/fusion-off dump | see log below | | |

Standalone, the fused norm kernel differs from the reference on 0.007% of
elements by one fp16 ulp with zero bias and an exact residual, and the GEMV
is within one ulp of cuBLAS. The probe simply amplifies any one-ulp
perturbation on near-random text (flat next-token distributions flip the
argmax), so neither change is worse than the other, but neither is
byte-exact. Because the round is host-bound today, the fusion's GPU saving
buys no wall-clock either, so:

- **on by default (exact):** `skinny_ar` plain all-reduce, `gdn_split3`,
  CPU pinning;
- **off by default, available:** `VLLM_SKINNY_BA_GEMV=1` (GEMV),
  `VLLM_SM70_TP2_AR_GEMMA_RMS_FUSION=1` (fused all-reduce + norm). Turn
  them on once the host path is fixed and after a teacher-forced KL check on
  natural text, which is the project's established gate.

# Concurrency, 2026-09-04

Boot: `--max-num-seqs 8`, graph captures 4/8/16/32 tokens, k=3, fp8 KV
(91k KV tokens), `VLLM_SKINNY_UNIFY_DENSE_MIN_M=17` so the M>16 band uses
the dense cuBLAS reconstruct instead of the WMMA reconstruct (whose 304 MB
transient OOMs the 16 GB card at 8 streams). MTP profiling on (costs ~8%).
Harness `scratchpad/concurrency_bench.py`: N concurrent 256-token greedy
streams, aggregate = tokens / (first token to last token).

| streams | verify rows M | NVFP4 route | target forward GPU | draft GPU | aggregate tok/s | per stream |
|---:|---:|---|---:|---:|---:|---:|
| 1 | 4 | qpn2 | 22.1 ms | 4.7 ms | 96.7 | 96.7 |
| 2 | 8 | qpn2 | 25.9 ms | 4.8 ms | 89.3 | 45-53 |
| 4 | 12-16 | qpn (legacy, 2x slower) | 40.3 ms | 9.8 ms | 142.2 | 36-45 |
| 8 | 20-32 | dense reconstruct | 127 ms at M=20 | 12.1 ms | crash: OOM in the reconstruct path | - |

Two separate problems:

1. **Host time explodes with more than one request.** At N=2 the GPU work
   per round is ~33 ms but each stream advances 3.46 tokens per ~71 ms, so
   ~38 ms per round is host time (vs ~5 ms at N=1). The fork's decode fast
   paths (`_e5_fast_prepare_v2`, single-request slot mapping, greedy token
   fast path, persistent metadata) are written for `num_reqs == 1` and fall
   back to generic per-request Python loops otherwise. This is why two
   streams are slower in aggregate than one.
2. **Weight-kernel route cliffs with speculation.** The verify batch is
   N x (k+1) rows: 9-16 rows land on the first-generation `qpn` kernel (the
   README's known MT=2 gap, 2x slower), and >16 rows leave the packed
   kernels entirely for a per-forward dense reconstruct of the whole NVFP4
   trunk (127 ms per forward at M=20, plus transients that OOM at M=32).
   Porting MT=2 to QPN2 and adding a chunked QPN2 (as QPN8 has) up to
   M~32 would keep 8 streams x k=3 on the packed path.

Without speculation the batch is N rows, so 8 streams stay on qpn2; that
sweep follows below.

Speculation off (`--max-num-seqs 8`, captures 1/2/4/8, `custom_ops` none so
the gated norm is unfused, otherwise the same box):

| streams | rows M | aggregate tok/s | per stream |
|---:|---:|---:|---:|
| 1 | 1 | 53.8 | 53.8 |
| 2 | 2 | 100.4 | 50.2 |
| 4 | 4 | 157.5 | 40-46 |
| 8 | 8 | 245.6 | 31-40 |

Near-linear: eight streams share each weight pass and the batch stays on
qpn2. **Crossover: k=3 wins only for a single stream (105-113 vs 54); from
two streams up, speculation off is faster in aggregate (100 vs 89 at N=2,
158 vs 142 at N=4, 246 vs a crash at N=8).** Until the fork's multi-request
host paths and the M 9-32 QPN2 band exist, serve concurrent traffic with
MTP off and `--max-num-seqs` 8, and single-stream traffic with k=3.

# DFlash2 (1Cat-vLLM 1.5.0) on this box, 2026-09-04

Drafter `incoai/Qwen3.8-27B-DFlash2` @ `dedf8df6` (BF16, 3.85 GB: 5 layers,
hidden 5120, non-causal block model, block size 7, selector top-K 16), now
under `Qwen3.8-27B-DFlash2/`. The 1.2.2 fork only registers the v1
`DFlashDraftModel`; `DFlash2DraftModel` needs 1.5.0 (`qwen3_dflash2.py`,
`dflash_sm70.py`, proposer/rejection-sampler changes: ~49 DFlash commits).

Attempts on the stock 1.5.0 env (`skinny15`), TP2, target KV e5m2 as in
upstream's recipe:

| attempt | outcome |
|---|---|
| 16k window, GMU 0.90 | OOM on the 16 GB card during load: `sm70_f16_prepare` of an fp16 LM head (1.19 GiB) on top of 13.8 GiB of weights per rank |
| 8k window, GMU 0.95, `VLLM_SM70_ENABLE_LM_HEAD_FASTPATH=0` | same OOM (that flag does not gate the prepare) |
| drafter unsharded on the 32 GB card (`draft_tensor_parallel_size: 1`) | same OOM; both ranks still report 13.8 GiB |
| `VLLM_SM70_LM_HEAD_TOP1=0`, `VLLM_SM70_DFLASH2_QPN8_RERANK=0` | loads at 12.6 GiB/rank, then refuses: **"DFlash2 requires an unquantized target LM head for candidate TopK; got ModelOptNvFp4LinearMethod"** |

So upstream's DFlash2 needs a full-precision target LM head for candidate
selection (1.2 GiB per rank at TP2 for this vocab), and target + drafter +
that head + its prepare transient do not fit a 16 GB card. It is not a
config problem; it is the memory shape of their implementation on this box.

What it would take here: port the DFlash2 model class and the proposer
changes into the 1.2.2 stack and feed the selector from the QPN2 LM head's
logits instead of an fp16 head. Memory then works out (target 10.9 GiB +
drafter 1.9 GiB per rank + KV for a 16-32k window). Expected payoff from
upstream's acceptance (~4.5 tokens per round vs 3.46 for k=3) and our round
costs (one 5-layer draft forward ~3-4 ms GPU vs three MTP steps ~4.7 ms;
verify at M=8 instead of 4, +1.5 ms): roughly 130 tok/s single-stream if
the host side stays at today's ~5 ms per round, which upstream's own notes
say required a series of verifier fast paths. One to two days of engine
work, not started.

# Stock 1Cat-vLLM 1.5.0 vs this stack, MTP k=3 only (no DFlash), 2026-09-04

Same box, same CLI shape (k=3 chain-MTP, greedy draft, captures [4,8],
`custom_ops=['none','+rms_norm_gated']`, MNS=1). Stock 1.5.0 is the unmodified
upstream wheel (env `skinny15`), 32k window (its KV budget), `fp8` resolving to
e5m2. Ours: E4M3 KV, 64k, all fork patches at shipped defaults. Decode is
`decode_bench.py 256 3` (311-token prompt, ignore_eos), measured back to back.

| | this stack (1.2.2 + patches) | stock 1.5.0 |
|---|---:|---:|
| decode, single stream, k=3 | 105 tok/s (86-120; ~30 ms/round) | 55 tok/s (45-61; ~58 ms/round) |
| prefill 464 tok | 838 | 947 |
| prefill 1807 | 1178 | 943 |
| prefill 3632 | 1208 | 1001 |
| prefill 7226 | 1229 | 1001 |
| prefill 14506 | 1194 | 987 |

Acceptance length on 1.5.0 was 2.8-3.4 (its own SpecDecoding metrics), i.e.
the same drafter quality as ours (3.46), so the 2x decode gap is per-round
cost, not acceptance: no host-memory all-reduce (NCCL over PCIe each of the
~138 reductions per round), no fused QPN8 dequant, and its TurboMind weight
path. Prefill: 1.5.0 wins only on the sub-chunk 464-token prompt (single
chunk, its dense path launches faster); from 1.8k up ours is 17-23% ahead
and both sit on the same PCIe x8 all-reduce wall (~1000-1230 tok/s).
Conclusion: switching the backend to 1.5.0 as-is would roughly halve token
generation and cut prefill ~20%; the only reason to port is to reach its
DFlash2 code, and that would be a port of the DFlash2 pieces into this
stack, not the other way round.

# FP8 -> NVFP4 weight-only requantization: measured, rejected (2026-09-04)

Idea: the checkpoint streams 6.72 GiB of E4M3 projections per round (all
non-MLP projections: GDN in_proj_qkv/in_proj_z/out_proj and attention
q/k/v/o); NVFP4 would halve that (~3.9 ms of a ~30 ms round). Converter:
`scratchpad/requant_fp8_to_nvfp4.py` (weight-only, ModelOpt layout, e2m1
rounding validated bit-for-bit against the checkpoint's own NVFP4 codes; no
calibration needed because the SM70 path runs fp16 activations). Relative
RMS weight error of the conversion: 9.4% (out_proj), same order as the
existing NVFP4 MLPs. Three boots in sequence, same script, same prompts,
k=3, 311-token prompt, 256 tokens x 6 runs; KL probe = greedy top-5
logprobs on 7 prompts vs the production dump.

| checkpoint | FP8 modules left | decode tok/s | acceptance len | greedy first-divergence (7 prompts) | KL top-5 mean / p99 |
|---|---:|---:|---:|---|---|
| unmodified (control) | 208 | 105.8 | 3.19-3.30 | none | 0 / 0 (bit-identical to production) |
| x1: out_proj + o_proj -> NVFP4 (1.88 GiB fp8 -> 1.05) | 144 | 103.6 | 3.10-3.22 | 56, 93, 66, -, -, -, 34 | 1.1e-2 / 0.15 |
| x2: all 208 -> NVFP4 (6.72 GiB -> 3.78) | 0 | 86.3 | 2.41-2.70 | 1, 0, 0, 47, 45, 0, 1 | 1.6e-2 / 0.29 (only 94 comparable positions) |

Two findings:
1. Quality: even the "safe" output projections shift the distribution
   (KL 1e-2, greedy diverges on 4/7 prompts) and cost ~0.1-0.2 tokens of
   acceptance; converting the in-projections wrecks it (x2 diverges at
   token 0-1, acceptance 2.5). The FP8 tier in this checkpoint is
   load-bearing, not conservative.
2. Throughput: bytes saved did NOT turn into wall time. x2 streams ~3.4 GB
   less per round yet its round is ~29 ms like the control (11.5 ms/tok x
   2.55). Consistent with the decode round being host-bound at ~30 ms:
   GPU-side savings land in idle gaps until the host path is shortened.
   Weight-byte levers (this one, 128-bit prepack) are gated on the host
   gap work; acceptance-length levers (k sweep, DFlash2) are not.

Serve script: `QPN8_PER_RANK` now overrides the census gate's per-rank
count (default 128) and `QPN8_PER_RANK=0` skips the dispatch gate; defaults
unchanged. The x1/x2 checkpoints (`Qwen3.8-27B-NVFP4-x1`, `-x2`, 18-20 GB
each) are left on disk for inspection and can be deleted.

## Correctness bug found and fixed: prompts of exactly k+1 tokens

Found by the k=4 KL probe ("The capital of France is" = 5 tokens -> " France,
1940-1944, ..."). Reproduced on production at k=3 with every 4-token prompt
(`scratchpad/diag_len.py`): N=4 corrupt and nondeterministic across
repeats, N=2,3,5..24 fine. Bisect: unchanged with the e5 cache off;
correct with `VLLM_SM70_QWEN_GDN_SPEC_DECODE_PIECEWISE=1` (FULL replay
excluded -- which also drops decode to 15 tok/s, so FULL replay must stay).
Cause: `_is_uniform_decode` (upstream heuristic) classifies a single
request with max_query_len == k+1 as a uniform (speculative-verify) decode
batch; a fresh (k+1)-token prompt therefore replays the FULL verify graph
with stale persistent attention/GDN metadata. Also reachable by a chunked
prefill whose tail chunk is k+1 tokens.
Fix (`fork_patches/gpu_model_runner.py`, in
`_determine_batch_execution_and_padding`): never treat a batch as uniform
decode when any request has num_computed_tokens < num_prompt_tokens
(runtime path only; capture keeps its explicit override). Verified: k=3
N=4 correct, KL 0 / bit-identical to production on the 7-prompt probe,
decode unchanged (106.0 / 105.6); k=4 N=5 correct, 114.3 / 113.2 tok/s.
Deployed to the env and running in production.

## Host-side profile of the decode round (lever 4)

Tools: the fork's `VLLM_SM70_E5_PROF` phase ledger, plus an in-process
main-thread sampler (`scratchpad/pysample/sitecustomize.py`, no ptrace
needed; ptrace_scope=1 blocks py-spy here). Findings:
- The engine core is idle: ~100% of its decode time is `_wait_for_response`
  (scheduler CPU < 0.3%). The critical path is the rank-0 worker's main
  thread, which is ~90% busy during decode: the round is host-LAUNCH-bound
  (Python driving ~1,600 kernels + metadata), ~30 ms/round vs ~27 ms GPU.
  Piecewise instead of FULL for the target costs 65 ms/round more -- the
  same phenomenon at scale.
- Where the worker's time goes (share of busy time): drafter `propose` 41%
  (per-step attention metadata rebuild 7%, top-token sampling incl. an NCCL
  all-gather per step 11%, launches/replay the rest); target prepare 33%
  (e5 fast prepare 11%, `_e5_apply_ints` 5%, `_build_attention_metadata`
  7%, `_update_smallq_decode_metadata` 10%); target logits/all-gather 13%;
  rejection sampler 3.5%; state update 4%.
- e5p ledger (profiler-inflated): prepare H2H4 6.7 ms, verify submit 1.2,
  drafter window 27, GPU verify 22, rejection 0.9, drafter tail 5, bubble
  (GPU idle between rounds) 8.6.

What would close it: persistent-metadata fast path for the drafter steps
(the MTP layer is full attention, same shape as the target's e5 path) and
folding the top-1 all-gather into skinny_ar (the fork's
`VLLM_SM70_TOP1_CUSTOM_AR` hook expects a `ca_comm.custom_top1_argmax`);
together ~10-12 ms of host per round. Only after that do the tail fusions
(lever 3, -6 ms GPU) and 128-bit weight loads (lever 5, ~-2.5 ms GPU) turn
into wall time. Not started.

# Concurrency, round 2 (2026-09-05): qpn2 MT kernel

`kernels/skinny_kernels.cu: skinny_nvfp4_qpn2_mt<SPLITK,NACC,MT>` -- qpn2
with MT in {2,4} m8n8k4 row-tiles against one decoded weight fragment,
M 9..16 (mt=2) and 17..32 (mt=4). Routed in `marlin.py` as `qpn2mt`
(`VLLM_SKINNY_QPN2_MT=0` disables). Every row is bit-identical to qpn2's
(verified on all trunk shapes, M 1..32), so multi-request verify logits
match the single-request kernel row for row.

What it did NOT do: amortise the weight stream. Measured (gate_up shape,
ms): qpn2 M=8 0.081; mt2 M=16 0.174; legacy qpn M=16 0.171; chunked 2x
qpn2 0.167; mt4 M=32 0.331; chunked 4x 0.330. The m8n8k4 loop is
issue-bound above 8 rows, not DRAM-bound (the FP8 twin's comment assumed
otherwise), so time grows ~linearly in row tiles. The fork's WMMA kernel
is no better in the band (0.166 / 0.285 ms at M=16 / 32 with resident CT
codes, and needs a 1 ms unprepack in UNIFY mode). None of the existing
kernels gets near the 48 us bandwidth floor above 8 rows; a genuinely
row-amortising small-M NVFP4 GEMM would be a new kernel design.

What it did do: M 17..32 no longer dense-reconstructs per forward (which
cost ~1.2 ms per projection and OOM'd at 8 streams). k=3 concurrency sweep
(`concurrency_bench.py`, MNS=8, captures 4/8/16/32, no profiler):

| streams | aggregate tok/s | per stream | acceptance | before (2026-09-04) |
|---:|---:|---:|---:|---|
| 1 | 113 | 113 | 3.27 | 97-113 |
| 2 | 119 | 60-73 | 3.27 | 89 |
| 4 | 176 | 44-61 | 3.08 | 142 |
| 8 | 138 | 22-26 | 2.77 | OOM |

Eight streams now run but lose to four: 32 verify rows cost 4x the 8-row
forward and the host path is generic. A 512-token N=4 run then OOM'd the
16 GB card on a 170 MiB prefill-reconstruct transient at GMU 0.92 with
MNS=8; concurrency boots should use GMU 0.90.

Round-time accounting from these numbers (round = acceptance / per-stream):
- N=1: ~28 ms at every k -> host-launch-bound, drafter steps nearly free.
- N=2..4 with any k>0: 44-62 ms. k=1 at N=4 is 44 ms with only ~25 ms of
  GPU work (8-row verify), so the multi-request speculative host path costs
  ~45 ms/round on its own. MTP off at N=4 is 25 ms.
- N=4 k=3: 62 ms, GPU-bound (16-row verify ~40 ms; the rank-0 worker spends
  28% of its busy time in a GPU-event wait). Both ranks profile identically;
  the engine core is 99% idle at N=4.

Where the N=4 host time goes (in-process sampler, share of worker host
time): `_prepare_inputs` 38% (GDN metadata build 12%, Flash-V100 build +
small-q metadata 8%, generic per-request prep the rest), drafter propose
28% (per-step metadata 8%, top-token sampling 7%), logits 9%, graph replay
6%. The single-request e5 fast path (`_e5_md_hit` requires num_reqs == 1)
and the GDN fast build (DFlash ddtree only, num_reqs == 1) are both off at
N>1; the e5 reject counter at N=4 reads `shape: 188`.

Conclusion. Reaching ~80 tok/s per stream at four streams (a ~40 ms round
at k=3) needs BOTH: (1) the multi-request speculative host path brought
from ~45 to <40 ms/round -- an N-request generalisation of e5 (persistent
attention/GDN metadata + in-place moving ints); and (2) a 16-row NVFP4
GEMM at ~1.2x the 8-row cost -- a new kernel design, since m8n8k4 (qpn2,
qpn2_mt, legacy qpn) and the WMMA kernel are all issue-bound at ~2x.
(1) alone lifts N=2-3 (N=2 would go to ~200 aggregate); (2) alone lifts
N>=4. Neither is started. Current recipe stands: k=3 (or k=4) for a
single user; MTP off for batch traffic, where 8 streams give 246.

## Row-amortising small-M kernels: found (2026-09-05)

Hypothesis tested: qpn2's per-row cost above 8 rows is A (activation)
re-read traffic -- every N-tile CTA streams the whole x through L2, which
already equals the weight traffic at M=8 and doubles with M -- not the
m8n8k4 issue rate. Fix: each warp owns T=2 adjacent N-tiles and loads the A
fragments once per k-group for both (`skinny_nvfp4_qpn2_mtt`,
`skinny_fp8_qpn8_mtt`; split-K partials staged in dynamic shared memory,
reduced in warp order -> deterministic, and bit-identical per row to
qpn2/qpn8 at equal (splitk, nacc), which is how they are routed).

ms per call, 32 GB card, weights resident (old = the previous best in the
band: qpn2_mt / qpn8_mt2 / chunked):

| shape | M=8 (base) | M=16 old -> mtt | M=32 old -> mtt |
|---|---:|---:|---:|
| NVFP4 gate_up K=5120 N=17408 | 0.082 | 0.173 -> 0.117 | 0.331 -> 0.228 |
| NVFP4 down K=8704 N=5120 | 0.053 | 0.097 -> 0.093 | 0.247 -> 0.171 |
| NVFP4 lm_head K=5120 N=62080 | 0.243 | 0.482 -> 0.374 | 1.065 -> 0.732 |
| FP8 in_proj_qkvz N=8192 K=5120 | 0.053 | 0.091 -> 0.056 | 0.243 -> 0.082 |
| FP8 out_proj N=5120 K=3072 | 0.051 | 0.043 -> 0.036 | 0.241 -> 0.053 |
| FP8 attn qkv N=7168 K=5120 | 0.051 | 0.088 -> 0.055 | 0.271 -> 0.082 |

FP8 (6.7 GiB of the per-round bytes) is now nearly flat to 16 rows and 1.5x
at 32; NVFP4 is 1.4x at 16 under the bit-identical config (a (16,2) config
reaches 1.25x on gate_up but breaks row identity with the M<=8 path, so it
is not used). Routed as `qpn2mt` (marlin.py, M 9..32, `VLLM_SKINNY_QPN2_MT=0`
off) and `qpn8-mtt` (modelopt.py, M 9..32, `VLLM_SM70_QPN8_MTT=0` off).
